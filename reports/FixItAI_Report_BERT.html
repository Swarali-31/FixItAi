Abstract

Technical support questions are often described as symptoms rather than exact error messages. Keyword search can miss relevant solutions when wording differs, while generative systems may provide advice unsupported by their sources. This project develops FixItAI, a local technical-support workspace that retrieves troubleshooting passages and displays their sources. The system combines a React interface, FastAPI service, lexical retrieval using TF–IDF and BM25, and a compact BERT bidirectional encoder initialized randomly with no pretrained weights. The supplied Stack Overflow archive contains 1,264,216 question rows, 2,014,516 answer rows, and 3,750,994 tag rows. The BERT run samples 200,000 questions; 173,857 usable question–answer pairs were selected using the highest-scored associated answer as a weak relevance label and divided into training and validation sets. A tokenizer was learned from the training text, and the BERT encoder produces normalized 128-dimensional representations optimized with symmetric in-batch contrastive loss on CUDA. The BERT experiment completed four CUDA epochs. Epoch 4 recorded Recall@1 6.30%, Recall@5 19.30%, and MRR 0.1313. The best recorded checkpoint by MRR was epoch 3 (MRR 0.1313). For context, a separate earlier scratch Transformer run completed four epochs and obtained MRR 0.0311, Recall@1 0.72%, and Recall@5 4.76%; those are not BERT results. The weak vote-derived labels do not establish technical correctness. Future work includes completing the BERT run and index, controlled lexical baselines, expert judgments, freshness metadata, and broader support documentation.

Keywords: Technical question answering; information retrieval; Transformer; contrastive learning; Stack Overflow; hybrid search; CUDA.

Model-status and reproducibility note: BERT training from random initialization completed four epochs on CUDA for the 200k-question sample. Its held-out retrieval metrics are reported from the saved training history. The prior four-epoch scratch Transformer results are shown only as a historical baseline. The existing application checkpoint remains a separate older model; the BERT checkpoint and full answer index will be deployable only after training and index generation finish. Lexical and hybrid baselines have not been benchmarked on the same split.

1. Introduction

Software users often describe a problem through a symptom, an unsuccessful workflow, or a short error message. Different users may describe the same underlying issue using different terminology, application versions, operating systems, and levels of detail. Developers, everyday computer users, and support teams all spend time locating and validating relevant guidance. Community question-and-answer archives contain practical troubleshooting knowledge, but their size and uneven post quality make manual search difficult [1], [2].

Term-based search is efficient and interpretable, but exact lexical overlap is weak when a question and its solution use different vocabulary. Dense retrieval can represent semantic similarity, while lexical signals preserve exact error strings, APIs, version numbers, and identifiers. Benchmark studies show that neither approach dominates every domain, motivating hybrid retrieval and domain-specific evaluation [3], [4].

Generative answer systems can produce fluent responses, but their reliability depends on whether retrieved evidence supports each claim [5]. FixItAI therefore returns ranked passages with source attribution rather than generating new instructions. This design makes evidence traceable and limits unsupported synthesis, but the system cannot answer well when relevant or current material is absent from its index.

The motivation is to build an end-to-end local support application and to evaluate a Transformer trained from random initialization on the available CUDA GPU without pretrained weights. The research gap is practical: many strong embedding systems depend on large pretrained models and extensive infrastructure, whereas a compact, locally trained, source-linked retriever is easier to inspect and reproduce on a student workstation. This is an engineering investigation, not a claim that the model is state of the art.

The objectives are to audit the supplied archive, form question–answer pairs, learn a tokenizer and Transformer from scratch, measure retrieval ranking, and expose search through a usable web interface. Major contributions are:

  • A local React/FastAPI workspace for technical search with source-linked passages.
  • A compact BERT bidirectional encoder initialized from random weights and trained on CUDA for question–answer retrieval (four-epoch CUDA training and evaluation completed).
  • A hybrid ranking pipeline combining TF–IDF, BM25, semantic similarity, and technology/error cues.
  • An explicit evaluation protocol and discussion of vote-label, sample-size, and GPU-memory limitations.

2. Literature Review

Recent software-support research targets question matching and answer recommendation. TopicAns combines topic-aware text representations with a pretrained encoder to reduce noise in long technical posts and reports gains in Precision@1 on four datasets; its extra topic model and pretrained model increase system complexity [2]. Que2Code retrieves semantically equivalent Stack Overflow questions before recommending code snippets, and includes automatic and human evaluation, but focuses on code fragments rather than general support prose [1]. Repo4QA links programming questions to GitHub repositories using dense retrieval; this addresses repository discovery, not direct answer-passage retrieval [6]. [7] compare representations for Stack Overflow tasks such as tag/API recommendation, showing that embeddings are task-dependent, while ProCQA adds community programming QA data and contrastive text/code alignment [8]. These studies establish the value of technical-community data but do not remove the need for a small local support tool with explicit evidence links.

Dense retrieval papers provide the modeling basis. DPR uses separate question and passage encodings trained to rank relevant passages [9]. SimCSE shows how contrastive learning can shape sentence embeddings [10], and Contriever demonstrates unsupervised contrastive retrieval across multiple domains [11]. E5 learns from weakly supervised text pairs and reports broad transfer across retrieval tasks [12]. ColBERTv2’s token-level late interaction improves fine-grained matching and reduces index size, but still carries a larger multi-vector storage and computation burden than a single-vector dual encoder [13]. Sentence-T5 also reports strong sentence-transfer performance, but uses pretrained text-to-text encoders [14]. FixItAI adopts a smaller single-vector architecture and accepts lower expected capacity in exchange for scratch training and local operation.

Benchmark research warns that embedding quality is task- and domain-dependent. BEIR found BM25 to be a robust zero-shot baseline while neural methods varied across datasets (Thakur et al., 2021). MTEB evaluates multiple embedding tasks and finds no universal model winner (Muennighoff et al., 2023). GTE reports strong general embeddings from multi-stage contrastive learning, and C-Pack contributes embedding resources and benchmarks for Chinese; both draw on much larger curated training resources than this project [15], [16]. BRIGHT evaluates reasoning-intensive queries and shows that leading retrieval systems can still perform poorly on complex technical questions [17]. Thus, falling training loss cannot substitute for held-out ranking or human review.

Further work explores richer retrieval and QA pipelines. Multilingual E5 trains on large multilingual text-pair collections, a possible direction for future language coverage [18]. Retrieve-then-read systems add a knowledge selector, and beam retrieval models multi-hop evidence selection [19], [20]; FixItAI currently performs single-stage passage retrieval and does not reason over multiple passages. The gap addressed here is therefore a reproducible low-resource application that combines transparent lexical evidence with a small scratch-trained semantic encoder. Its novelty lies in this constrained integration and evaluation, not a new loss or architecture.

3. Proposed Methodology

3.1 Overall System Architecture

The offline pipeline parses and cleans the archive, matches sampled questions to answers, learns BPE merges, trains a dual encoder on CUDA, evaluates ranking, then saves weights and the retrieval index. Online, a React client sends a query to FastAPI. The service analyzes technology names and error strings, combines lexical and semantic scores, reranks explicit matches, and returns passages with source metadata.

3.2 Dataset

The supplied data/archive.zip is 1,189,724,316 bytes (about 1.19 GB compressed and 3.60 GB uncompressed). The three CSVs are related tables, so their rows do not represent one common sample schema.

Questions are sampled with reservoir sampling using seed 42. The highest-scoring associated answer with at least 40 cleaned characters is retained; 173,857 pairs were found, while the unmatched sample entries are excluded. The archive data has no topic-class labels in this task, and it lacks an accepted-answer field in the columns used by this pipeline. This is therefore a retrieval dataset, not a classification dataset. No language detector or language distribution calculation was performed; multilingual coverage must not be claimed. Stack Overflow public user contributions carry applicable CC BY-SA terms, and the generated index preserves IDs, links, and attribution [21], [22]. Redistribution must comply with those terms.

3.3 Data Preprocessing

HTML is parsed to text, entities are unescaped, whitespace is collapsed, and fields are capped to control memory. Tag strings are cleaned, deduplicated, and sorted. The query concatenates title, tags, and cleaned body; the selected answer is its positive passage. A lowercasing, Unicode-NFKC, byte-level BPE tokenizer is trained on the training split only, with vocabulary target 12,000; inputs are truncated/padded to 128 tokens. No stop-word removal, stemming, lemmatization, POS tagging, NER, or emoji-specific handling is performed. Subword tokenization helps represent rare forms without a manually engineered word vocabulary [23].

3.4 Feature Engineering

The BERT encoder maps token sequences to contextualized hidden states; attention-mask mean pooling and L2 normalization produce 128-dimensional retrieval vectors. The same encoder processes questions and answers; dot products represent semantic compatibility. Lexical features use scikit-learn TF–IDF with unigrams/bigrams and sublinear term frequency [27], plus BM25. When neural vectors are available, the application's base hybrid score is 0.25 TF–IDF + 0.25 normalized BM25 + 0.50 semantic similarity. Technology tags and exact error mentions contribute additional reranking cues. Lexical matches complement semantic similarity for identifiers and error codes [24]–[26].

3.5 Model Development

The current model is a compact BERT bidirectional encoder built with the BERT architecture and initialized from random weights; no pretrained checkpoint is downloaded or loaded. Configuration: hidden size 128, two encoder layers, four attention heads, feed-forward width 512, dropout 0.1, and maximum sequence length 128. The tokenizer is learned from the project’s training split. Attention-mask mean pooling and L2 normalization yield 128-dimensional question and answer embeddings. AdamW (learning rate 2×10−4, weight decay 0.01), batch size 8, gradient clipping 1.0, CUDA FP16 autocast, and gradient scaling are used. Symmetric in-batch contrastive cross-entropy with temperature 0.07 treats paired questions and answers as positives and other answers in each batch as negatives. This is project-specific retrieval training of a randomly initialized BERT encoder; it is not the original large-scale masked-language pretraining procedure and it does not generate text [10], [28], [38].

The BERT training process uses the NVIDIA RTX 3050 Laptop GPU and the 200k-question archive sample. The BERT CUDA run completed 4 epochs. Its best recorded checkpoint is epoch 3 with Recall@1 6.60%, Recall@5 19.60%, and MRR 0.1313. The earlier scratch Transformer run is a separate model and its metrics are identified only as historical baseline results in Section 5. Neural model training and embedding operations require CUDA and fail if CUDA is unavailable; archive parsing, HTML cleanup, tokenization, TF–IDF, and BM25 are CPU-side input and retrieval tasks. The model uses the Hugging Face Transformers BERT implementation [29], [30].

3.6 Proposed Novelty

The project contribution is a source-attributed local support retriever that combines a compact BERT bidirectional encoder, initialized randomly and trained on CUDA for contrastive question–answer ranking, with lexical search and error/technology cues. The contribution is the application and its constrained training/evaluation workflow, not a new BERT architecture or language-model pretraining objective.

5. Results and Discussion

Recall@1, Recall@5 and mean reciprocal rank (MRR) evaluate ranked retrieval. Accuracy, ROC-AUC, and a confusion matrix are not primary metrics for this single-positive retrieval setup. The earlier Transformer baseline used 2,500 validation queries; BERT is evaluated on 1,000 held-out queries against all 173,857 candidate answers. A high rank means agreement with the highest-voted-answer proxy, not verified correctness.

The interface provides Home, Ask FixItAI, Knowledge Base, Model Evaluation, Search History, and About pages. Ask FixItAI returns ranked passage text, source attribution/link, technology tags, match terms, and component scores. The Knowledge Base page browses indexed and uploaded documents. The tool retrieves; it does not generate an answer. Figure 2 shows a genuine screenshot of the running React application; the model deployment caveat is stated in its caption.

6. Comparative Analysis

Across checkpoints, MRR rose from 0.0193 at epoch one to 0.0316 at epoch three, then measured 0.0311 at epoch four; Recall@5 rose from 2.64% to 4.76% across the run. The application gives semantic similarity half of its hybrid base score and retains lexical matching for exact technical terms. This is a design hypothesis, not proof of superiority. A same-split comparison among TF–IDF, BM25, semantic-only, and hybrid ranking plus human judgments is required. Existing benchmarks show substantial domain variation, so general benchmark scores cannot be substituted for this project-specific test [3], [4].

9. Limitations

  • The archive is sampled: 200,000 of 1,264,216 questions were considered for training; this is not the full question dataset.
  • The highest answer vote is a weak label, not an accepted-answer or correctness guarantee. It can encode popularity and age effects.
  • Only 2,500 validation queries are evaluated, on a random split. There is no temporal, cross-domain, or expert-judged assessment yet.
  • The model is small relative to pretrained embedding systems; its low metrics and narrow scope limit reliability.
  • The 4 GB laptop GPU caused an out-of-memory error during the first epoch-four attempt. Epoch four was resumed with batch size eight and a fresh optimizer state. The final corpus-embedding/index build then failed with a host memory-allocation error, so the 200k model is not the model currently served by the app.
  • Text preparation/tokenization and lexical retrieval use CPU; GPU-only applies to neural training/inference, not every pipeline operation.
  • Archive content may be stale or omit Teams, device, and vendor-specific guidance. The retriever cannot verify current procedures.
  • CC BY-SA attribution and share-alike terms need to be respected for redistributed material.

10. Future Scope

Run controlled TF–IDF/BM25/semantic/hybrid ablations and obtain technical reviewers’ relevance and correctness labels. Improve supervision with accepted-answer metadata where available, expert-curated pairs, freshness dates, and answer edits. Add licensed vendor and productivity-app documentation with version metadata, then evaluate multilingual coverage rather than assuming it. Improve scalable vector indexing and incremental document updates. Add periodic checkpointing of optimizer/scaler state and training logs. A later answer-generation stage should only be considered if it cites retrieved evidence and is evaluated for unsupported claims.

11. Conclusion

FixItAI is a local technical-support retrieval workspace designed to help users find source-linked troubleshooting guidance from symptoms, application issues, and error messages. The application combines a React/Vite interface, FastAPI service, technical passage library, lexical ranking, and a neural semantic retrieval model. It returns ranked passages with attribution rather than generating unsupported advice. The research and implementation cover NLP sequence models and the CO4/CO5 course topics, with a BERT encoder selected and training on the retrieval task underway.

The supplied Stack Overflow archive contains 1,264,216 question records, 2,014,516 answer records, and 3,750,994 tag records in separate CSV files. The BERT experiment samples 200,000 questions and uses the highest-scored associated answer as a weak relevance label. A tokenizer is learned from the training split. The BERT architecture is initialized from random weights without pretrained checkpoints and trained on the NVIDIA GeForce RTX 3050 Laptop GPU using symmetric in-batch contrastive question–answer loss. The BERT CUDA run completed 4 epochs. Its best recorded checkpoint is epoch 3 with Recall@1 6.60%, Recall@5 19.60%, and MRR 0.1313.

A separate earlier scratch Transformer run provides historical context only: it completed four epochs and recorded Recall@1 of 0.72%, Recall@5 of 4.76%, and MRR of 0.0311 on 2,500 held-out queries against 173,857 candidate answers. These measurements belong to that earlier model and must not be attributed to BERT. Both experiments rely on vote-derived labels that do not establish technical correctness. The project has implemented the user-facing retrieval application and completed a four-epoch from-scratch CUDA BERT training experiment with held-out retrieval evaluation; same-split TF–IDF/BM25 comparisons and deployment of the BERT index remain the next steps. Future work will record the completed BERT run, build the index in memory-safe batches, compare rankers on identical data, and evaluate answer usefulness with expert-reviewed labels and current licensed technical documentation.

CO4 AND CO5 COURSE COVERAGE

CO4 — Recurrent Neural Networks and Language Models. Recurrent networks process token sequences through a state carried from earlier steps; classic work describes this recurrent memory mechanism [34]. Long-range learning in plain RNNs can suffer from decaying gradients. LSTM gates were introduced to preserve error flow over longer intervals [35], while GRU is a simpler gated recurrent variant studied alongside LSTM [36]. FixItAI does not implement an RNN, LSTM, or GRU. Its current question and answer representation model is a BERT bidirectional encoder initialized randomly and being trained from scratch; the RNN topics provide architectural context for comparing sequence models.

CO5 — Machine Translation, Seq2Seq, BERT/GPT/LaMDA, and Conversational AI. Seq2Seq encoder-decoder models learn to map source sequences to target sequences and were demonstrated for machine translation [37]. BERT uses bidirectional masked-language pretraining [38], whereas GPT uses autoregressive generative pretraining [39]; LaMDA is a Transformer language model specialized for dialogue [40]. FixItAI uses a BERT bidirectional encoder trained with a project-specific contrastive retrieval objective (four-epoch CUDA training and held-out retrieval evaluation are complete). It neither translates text nor generates dialogue. Retrieval can serve as one component of conversational AI, but FixItAI currently returns sourced passages without a dialogue manager or generative response. The training objective is not the original BERT masked-language-model pretraining procedure.
